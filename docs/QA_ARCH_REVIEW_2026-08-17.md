## Найденные дефекты

### QA-001 — Critical — межпрограммная утечка отчётных данных

Пользователь `auditor2`, закреплённый за программой ID 2 «Отдел качества», успешно получает `/api/reports/dynamics?questionnaireId=1&programId=2`, где questionnaire ID 1 относится к программе ID 1 «Эпидемиология».

Фактический результат: HTTP 200, 20 критериев и 3 отдела чужой программы. Параметр `programId` контролируется клиентом и в `dynamics` вообще не используется. Сервер доверяет произвольному `questionnaireId`.

Риск: утечка медицинских/кадровых результатов между направлениями; тот же архитектурный паттерн присутствует и в других report/list endpoints, где область доступа формируется из query-параметров клиента.

Ожидаемо: backend извлекает программу из `ctx.state.user`, запрещает чужой questionnaire/department и никогда не использует клиентский `programId` как источник авторизации. Для чужого объекта — 403 либо 404.

### QA-002 — High — некорректные даты приводят к HTTP 500

Запрос `from=banana&to=tomato` возвращает HTTP 500 `InternalServerError`.

Ожидаемо: строгая проверка ISO-даты `YYYY-MM-DD`, реальности календарной даты и `from <= to`; ответ 400 с понятным сообщением. `questionnaireId=abc` также должен давать 400, сейчас возвращается 200 с пустыми данными. Обратный период сейчас молча даёт 200 и пустой набор.

### QA-003 — High — поле `sessions` содержит число субъектов, а не сессий

Для employee-questionnaire ID 3 сводка сообщает 3 сессии и 10 субъектов. Сумма `departments[].cells[].sessions` в dynamics равна 10. Значение увеличивается один раз на `tracer-subject`, поэтому подпись и контракт неверны.

Ожидаемо: считать уникальные session ID на отдел/месяц либо переименовать поле в `subjects` и скорректировать UI/экспорты.

### QA-004 — High — гонка запросов и экспорт устаревших данных

При быстрой смене трейсера, отдела или периода предыдущий запрос не отменяется и не маркируется request ID. Более старый ответ способен перезаписать новый. Пока новый запрос выполняется, старые данные остаются видимыми (`loading && !data`), а кнопки Excel/PDF остаются активными.

Риск: пользователь видит или экспортирует отчёт с заголовком новых фильтров, но данными предыдущих фильтров.

Ожидаемо: AbortController/request sequence, очистка или визуальная блокировка старого набора, отключение экспорта во время загрузки; тест с искусственно переставленными ответами.

### QA-005 — Medium — отделы агрегируются по имени

Map отделов индексируется `department.name`. Одноимённые отделы разных организаций/ID будут объединены, а в результате останется ID первого отдела.

Ожидаемо: ключ — стабильный department ID; snapshot-отделы без relation должны иметь отдельный составной ключ и явно обозначенный статус.

### QA-006 — Medium — отсутствующие scorePercent превращаются в 0%

`Number(sub.scorePercent ?? 0)` считает отсутствующую оценку провалом и искажает средние/тренд. Это особенно опасно для старых или частично мигрированных данных.

Ожидаемо: null/undefined/NaN исключаются из среднего и отдельно учитываются как записи без оценки; политика должна быть зафиксирована в контракте.

### QA-007 — Medium — жёсткий `limit: 1000000` и агрегация в памяти

Endpoint загружает до миллиона сессий, затем до миллиона субъектов с JSON-ответами и relation populate, после чего агрегирует всё в одном Node.js процессе. Это создаёт риск исчерпания памяти, длинных пауз GC и тайм-аутов на production PostgreSQL.

Ожидаемо: ограничить допустимый период, агрегировать SQL-запросами/батчами, ввести timeout/observability и нагрузочный бюджет. Индексы нужны минимум на session(questionnaire, date, department) и subject(session, employee).

### QA-008 — Medium — 24 месяца отображаются, но читаются все данные периода

`monthsBetween` обрезает сетку до последних 24 месяцев, однако запрос к БД читает весь запрошенный период. Пользователь не предупреждён, что ранние месяцы отброшены; сервер всё равно несёт стоимость полного диапазона.

Ожидаемо: либо отклонять диапазон >24 месяцев, либо корректировать `from` до фактического окна и возвращать явный metadata-флаг truncation.

### QA-009 — Medium — неоднозначная классификация тренда

Тренд определяется только разницей первой и последней непустой точки и порогом 15 п.п. Длинный провал между ними игнорируется; «persistent» назначается только если абсолютно все точки <60. Две проверки в одном месяце также превращаются в «мало данных», хотя наблюдений может быть много.

Ожидаемо: согласовать бизнес-определение (линейный наклон, минимальное число месяцев/наблюдений, устойчивость последних N периодов), вернуть основания классификации в API и покрыть таблицей unit-тестов.

### QA-010 — Low/Medium — PDF с 24 месяцами не имеет стратегии разбиения

Все месяцы помещаются в одну landscape-таблицу с шириной `auto`. Для 24 колонок плюс текст/тренд ожидаемы нечитаемый масштаб или проблемы компоновки.

Ожидаемо: разбивка по 6–12 месяцев на страницы, повтор заголовков, тест фактического файла и визуальная регрессия.

### QA-011 — Low — React/ESLint предупреждения в изменённом коде

Новая вкладка добавляет синхронные setState внутри effects. Это не ломает build, но усиливает лишние рендеры и усложняет устранение гонок. Всего lint показывает 9 предупреждений, 0 ошибок.

## Архитектурная оценка

Разделение на API-агрегацию, типизированный frontend-контракт и отдельный export-модуль разумно для текущего масштаба. Основная проблема — граница доверия: фильтрация по программе реализована как UI/query concern, а должна быть обязательной серверной политикой доступа. Вторая проблема — endpoint одновременно выполняет выборку, нормализацию исторических snapshot, расчёт метрик и классификацию тренда; без выделенного доменного сервиса это трудно модульно тестировать и безопасно оптимизировать.

Рекомендуемая целевая схема:

1. Policy/service `reportScopeForUser(ctx.state.user)` вычисляет разрешённые program/questionnaire/organization IDs.
2. DTO validator нормализует ID и даты, ограничивает диапазон.
3. Repository выполняет агрегированные/батчевые запросы без миллионных populate.
4. Pure domain functions считают compliance/trend; для них создаётся матрица unit-тестов.
5. Controller только связывает validation, authorization, service и response DTO.
6. UI использует отменяемые запросы и атомарное состояние `{filters, data, requestId, status}`.
